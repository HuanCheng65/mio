# 澪 Agentic 运行时设计

> **Version**: Draft — 2026-10-24
> **Status**: 设计中，未实现
> **参考**: Anthropic《Effective context engineering for AI agents》《Writing effective tools for agents — with agents》

---

## 0. 为什么要改

现在的一轮回复是一次性的：代码把记忆、群文化、人物印象全部预先塞进 prompt，模型吐出一个 `{thought, urge, search, actions}` JSON，代码再用正则抠出来执行。这带来几个结构性问题：

1. **行动空间只有"开口"**。澪能做的事只有 message / reply / react / sticker，"想做点什么"的冲动只能变成说话，于是要靠 `urge` 打分和一长串"别插嘴"的规则硬压。
2. **记忆是推送的，不是取用的**。每轮都注入全部相关记忆，既占注意力预算，又让模型没法在需要时多想一步。
3. **搜索只能一跳**。决定搜索就不能同时行动，搜完要整轮重来。
4. **前缀缓存基本失效**。每轮重新渲染最近 50 条消息、`[mN]` 从 1 重新编号、当前时间写在 system 里，前缀几乎每轮都变。

## 1. 原则

**她是什么样的群友**（写在人设开头，也是评测标准，按优先级）：

1. **活人感、有趣**：主动开口是正常的，好坏看时机和内容，不看话多话少。
2. **诚实**：不编事实，不冒领没做过的事（"我循环了好久""我打完了"）；也不主动强调自己做不到什么，只聊她知道、在意的那部分，被直接问到才说清楚。
3. **人设与设定**：在前两条之上的风味。
4. **情商**：什么时候说什么、什么时候闭嘴，是贯穿始终的底线。

**系统怎么实现她：**

- **唤醒之内交给模型，唤醒之外交给代码。** 何时唤醒、能说多少话、平台规则，是代码的硬约束；被唤醒之后看什么、想什么、记什么、说不说，由模型通过工具自主决定。
- **做点什么 ≠ 说点什么。** 工具让行动空间变大：查记忆、记一笔、收一张表情包、看一眼图，都是"做了事"但群里看不见。冲动有了不开口的出口，沉默才自然，而不是被规则压出来的。
- **上下文是有限的注意力预算。** 找最小的高信号 token 集合；能按需取用的就不预先塞。
- **渐进式披露。** 模型得先知道"有这段记忆"，才会去 recall。先给轻量的标识（标题、人名、时间），内容按需展开。
- **只追加，不重写。** 每个群一条只追加的 log，前缀稳定才吃得到缓存。

## 2. 验证结果（2026-10-24，deepseek-flash = V4.1-Flash-1017）

在服务器上用真实 key 跑的 spike，约 5k token 的前缀 + 3 个工具：

| 项目 | 结果 |
|---|---|
| 工具调用 | 可用，支持并行调用（一次发出两个 `recall`）；默认开启思考，每步 80–160 推理 token |
| 多步循环 | 回填 tool 结果后继续推理；第二步 5230 token 中 4992 命中缓存 |
| 工具 + 图片同请求 | 可用；一张 PNG 约 1000 token，单步 3.8 s |
| 只追加 log 的缓存 | 追加后只有尾部 170–200 token 未命中 |
| 前缀含图片的缓存 | 图片随前缀一起命中 |
| 单步延迟 | 1.2–3.8 s |

两点直接影响设计：

- **推理 token 计入 `max_tokens`**。`max_tokens: 64` 时 64 个全被推理吃掉、正文为空。上限必须覆盖推理。
- **模型偏爱 recall**。拿到 recall 结果后又追加了两次 recall。需要靠工具描述、返回内容的"足够感"和步数上限压住。

成本量级：一次约 5k token 的唤醒，缓存部分约 $0.000015，未命中尾部加输出约 $0.0001。

## 3. 上下文布局

```
[system]  人设 + 行为原则                      固定，按人设缓存
[tools]   固定工具集                            固定，按平台能力确定一次
[log]     本群的事件流，只追加：
  user       〔群速写〕常客 / 固定梗 / 氛围      第 1 层记忆，压缩时重写
  user       〔交接〕上一段的摘要                压缩时写入
  user       〔10-24 21:03〕
             [m1024] 白川#a3: 下周终于考完了
               └ 白川：挺熟的 · 记过 12 件事 · 上次聊 3 天前
             〔你隐约记得〕「白川的考试周」(10-12)
  assistant  tool_call recall("白川 考试")
  tool       「白川的考试周」10-12：十月底期末，暂停了音游
  assistant  tool_call remember(...)           没开口，但做了事
  user       〔10-24 21:07〕[m1025] ...
```

- **一个群一条 log。** 不同群的人设、群速写、平台都不同，本来就各自缓存。
- **消息编号用群内自增计数**，永不重排；`[m1024]` 在整段 log 里稳定指向同一条消息。
- **时间写在每批消息的头部**，system 里不放当前时间。
- **用户 ID 用短别名**（`白川#a3`），代码负责和平台 ID（官方 QQ 的 32 位 openid）互转。语义化的短 ID 比随机串更少认错，也省 token。
- **图片只在它出现的那一批里附原图**，之后的引用用 `[m1031 的图]`；需要再看时调用 `look`。
- **bot 自己说的话**以工具调用的形式留在 log 里，不需要再额外合成"[你之前说了]"的文字。

## 4. 记忆：三层渐进式披露

记忆设计 v5 里有一条："记忆不会被主动调用，而是在相关话题出现时自然浮现"。三层结构就是在实现这句话：第 2 层负责"浮现"，第 3 层是浮现之后她自己决定要不要细想。

### 第 1 层：常驻核心（相当于 CLAUDE.md）

log 开头的群速写：常客是谁、关系远近、几个固定梗、群的整体氛围。控制在几百 token。只在压缩时重写，位置固定，能被缓存。

### 第 2 层：随消息追加的线索

每批消息追加进 log 时，代码顺带附上：

- **人物卡片**：某人在本段 log 第一次说话时附一行（称呼、熟悉度、记过几件事、上次聊是什么时候），之后不再重复。
- **"隐约记得"**：用 embedding 拿本批消息去匹配记忆标题，只列最相关的 2–3 个**标题和日期**，不给内容。没有足够相关的就不列。

两者都追加在尾部，不破坏前缀。

### 第 3 层：工具按需展开

- `recall(query)` 返回几条匹配记忆的标题和一行摘要；`recall(id=…)` 展开一条的全部内容和来源消息。
- `person(name)` 一次返回对某人的综合了解：印象、记过的事、称呼、最近状态。

### 写入

- 唤醒中由澪自己 `remember`。每批消息本来就会唤醒一次，她看到值得记的事随手记，不再需要单独的"快速提取"调度。
- 写入前先找很像的笔记：有就不重复写，把那条给她看，让她用 update 改写成包含前后变化的一段（时间线叙事）。
- 睡眠回合（见 §7）负责整理：合并重复、更新印象和群速写、淡化不再重要的事。

### 存储：一个本子

`mio.note` 一张表：类型（事实 / 印象 / 事件 / 关于自己 / 表情包）、关于谁（平台 ID、群、我）、一句话标题、第一人称内容、出处（消息编号）、是否放在心里、向量、被想起的次数。

和记忆设计 v5 的关系：

- **保留的概念**：记忆有偏、模糊、会淡；什么值得记的几个维度（写进 `remember` 的描述）；第一人称带不确定的口吻；矛盾用时间线叙事；对人的多时间尺度印象；称呼学习；旁观者视角。
- **不再需要的机制**：工作记忆缓冲和内存里的短期情绪（log 本身就是工作记忆）、提取调度器、模型打出的重要度 / 情感 / 置信度分数、按次数算的熟悉度分级（改为人物卡片里的客观数据加她的印象笔记）、21 天过期和池上限（改由睡眠回合判断）、三张分开的表。
- **新增的概念**：
  - **主动回想**：v5 认为"记忆不会被主动调用"，但人也会主动去想；浮现（线索）和回想（`recall`）两条路都要有。
  - **关于自己**：她说过的观点、答应过的事、发起的梗、最近在意的东西。前后一致和喜好的演变都靠它。
  - **出处**：笔记关联原始消息编号，回想时能核对原话，避免凭空"记得"（诚实）。
  - **放心里**：有些事记得但不该随便提，比如别人难受时说的话；对方不提就不主动提（情商）。
- 表情包收藏也是一种笔记：她自己看图、自己写适合表达的感觉，不再单独识图。收藏不分群。

## 5. 工具

工具要少、职责不重叠、用自然语言参数。初版 8 个（`react` 只在 OneBot 上提供）：

| 工具 | 类型 | 作用 |
|---|---|---|
| `say(text, reply_to?)` | 对外 | 发消息；`reply_to` 引用某条 `[mN]` |
| `react(message, emoji)` | 对外 | 点表情回应；平台不支持时返回说明 |
| `sticker(feeling)` | 对外 | 从收藏里找一张发出去 |
| `recall(query \| id)` | 对内 | 回忆，见 §4 |
| `person(name)` | 对内 | 查对某人的了解 |
| `remember(kind, about, content)` | 对内 | 记一笔；`kind` = 事实 / 印象 / 事件 / 表情包收藏 |
| `search(query, kind)` | 对内 | 查作品、歌曲、梗；`kind` = anime / galgame / music / general |
| `find_source(message, image?)` | 对内 | 拿群里的图反查出处、画师（用录制时存下的原图） |

不调用任何对外工具，这一轮就是沉默。没有 `urge`，也没有"结束"工具。

**描述和返回值的写法：**

- 描述按"跟新同事解释"的口吻写清楚何时该用、何时不该用。`recall` 要明确："隐约记得里没出现、对话也没提到的事，通常不用去翻"。
- 返回值默认简洁，只给下一步决策需要的信息；需要细节时再用 `id` 展开。
- 被护栏拦住时返回能指导下一步的说明，而不是错误码，例如：`刚说过话，2 分钟内别再说了` / `这个平台不能点表情，可以用 sticker 或什么都不做`。

## 6. 唤醒与护栏（代码负责）

- **唤醒时机**：沿用 debounce（静默窗口 + 最短/最长等待）、被 @ 立即唤醒并打断进行中的思考。
- **每次唤醒的步数上限**：默认 6 步工具调用，到上限就结束本轮。
- **对外行动的限制在工具里执行**：冷却、每小时上限、连续发言上限、官方 QQ 的被动回复窗口与次数、平台能力。被拦时以工具结果告知模型。
- **群开关、影子模式**：沿用 `mio.on/off/shadow`；影子模式下对外工具返回"已记录"但不真正发送。
- **`max_tokens`** 覆盖推理，默认 2048；截断照旧直接报错。

## 7. 压缩与睡眠回合

- **触发**：
  - 群里安静 4 小时：相当于"一段对话结束"。社区实测 DeepSeek 缓存至少能留 6 小时以上（官方只说几小时到几天），这时睡觉大概率还在用缓存，睡眠本身很便宜；醒来面对的是一段短 log，缓存过不过期都无所谓。
  - log 达到 100k token：硬上限，在那次唤醒结束后睡，不拖慢回复。按估算，活跃群（每天约 500 条消息、50 张图）一天多到上限，安静的群要好几天；图片占了大头。
  - log 不足 8k token 就跳过；不另设每天固定时间。
- **睡眠回合**：同一个模型、同一套工具定义（换任何一样都会打掉缓存），追加一条睡前整理的说明，对外工具在这期间一律返回"不往群里说话"。她用记忆工具查重合并、更新印象、记下关于自己的事，最后写【群速写】和【交接】两段。格式不对就报错、不压缩，下次再试。
- **新 log** = system + 一条开头（群速写 + 交接 + 最近 30 条消息原文），lastSeq 沿用，消息编号接着往下。旧段保留在库里作记录，原始 tool 结果不再进上下文。
- **不做的**：不过度合并（会丢细节）；淡化看被想起的次数而不是只看时间，印象和关于自己的笔记不淡化（参考 Letta 社区的 sleeptime 实践）。每周一次的完整整理等回放评测看过记忆实际长成什么样再定。
- **缓存寿命实测**：每次请求记录距上次请求的间隔和命中情况，间隔超过 30 分钟的打 info 日志，用来校准安静阈值。

## 8. 实施计划

不在旧运行时上原地迁移：只追加的 log 和"每轮注入记忆"互相矛盾，log 一上线就需要压缩，而压缩又依赖睡眠回合写记忆，几块拆不开。新运行时放在 `src/agent/`，自底向上按模块搭，每个模块单独提交、单独测试，最后整体切换。

0. **录制**：事件存储 + 录制器 + `mio.record` 模式（只录不回、不需要模型配置），群开关指令移出 bootstrap。先部署到服务器积累真实群聊，图片随录随存。
1. **log**：在事件存储之上渲染每群的只追加 log：稳定编号、短别名与平台 ID 互转、按批渲染、token 统计。
2. **agent 循环**：OpenAI 兼容的工具调用、步数上限、被 @ 打断、影子模式。
3. **对外工具**：`say` / `react` / `sticker`，复用现有发送逻辑与被动回复检查。
4. **对内工具**：`search` / `find_source`，复用搜索服务。图片在 log 里一直都在，"回头再看一眼"放到第 6 步、压缩把旧图移出上下文之后再做。
5. **记忆**：`mio.note` 本子、`recall` / `person` / `remember`、人物卡片与"隐约记得"、表情包收藏。
6. **压缩与睡眠回合**：含群速写生成，取代提取调度器和每日蒸馏。
7. **回放评测**：用第 0 步录下的群聊回放给新运行时（真实模型），统计开口率、工具调用、token 与缓存命中，迭代工具描述。
8. **接入上线**：新增 `mio.agent` 模式（可影子），与旧运行时在服务器上对比；确认后删除旧运行时、JSON 提示词、提取调度器和 Gemini 显式缓存，不保留兼容代码。新运行时只支持 OpenAI 兼容的工具调用。

## 9. 评测

- **数据**：影子模式日志（`data/shadow/`）里的真实群聊片段。
- **任务样例**：
  - 群友提到上次说过的事 → 是否 recall、是否用对
  - 一晚上的普通水群 → 开口次数是否接近现状、有没有乱 recall
  - 有人发梗图 → 是否看懂、是否只 react 或沉默
  - 有人说了值得记的事 → 是否 remember、记得准不准
- **评分**：每轮按上面四条原则打分（像不像活人、有没有意思、有没有说假话或冒领经历、时机和分寸对不对），旧行为规则里"反复犯过的毛病"逐条转成用例。
- **指标**：每次唤醒的工具调用数与分布、开口率、token 与缓存命中率、单次唤醒延迟、护栏拦截次数。
- **护栏的定位**：代码里的冷却和上限只防刷屏失控，放得宽；开口时机交给人设和模型判断，不靠护栏塑形。
- 定期把对比 transcript 交给 agent 分析，用来调工具描述（工具那篇文章的做法）。

## 10. 待定问题

- 思考模式是否每轮都开：开着更稳，但每步多 100+ token、多几百毫秒。
- "隐约记得"的相关度阈值和条数，需要用评测确定。
- 长 log 里的图片：每张约 1000 token，要不要在压缩前就把旧图换成文字描述。
- 现有记忆表的数据是否需要迁移；目前服务器上没有旧数据，可以从零开始。
